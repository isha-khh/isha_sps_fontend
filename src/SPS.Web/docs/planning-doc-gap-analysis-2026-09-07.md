## 🟢 先講好消息：這些已經是真的做好、跑得動的東西

- **需求端公告徵案的自動配對通知**（規劃書「媒合服務構面」第二種模式）已經**完整實作**：`DemandService.PrepareNotificationRecordsAsync` 會拿需求的標籤跟供給端公司的標籤做 tag overlap，門檻 **30% 以上**才算配對成功，篩選出「啟用中、已審核通過的供給端會員」寄信通知，還會寫入 `DemandNotification` 表追蹤寄送狀態。這塊比想像中做得完整。
- **AI 向量語意搜尋**（規劃書「輔導串接型媒合」可以用得上）——`DemandService` 有 `GetSimilarCompaniesByVectorAsync`，`ContentEmbedding` 這張表存在，向量比對是真的做出來的，不是空殼。
- **應用情境/範疇/智慧技術標籤系統**——上次的推測（這一大串多選 checkbox 其實是通用標籤系統）在後端原始碼裡直接找到證據：`CompanyTagCategory`（企業↔標籤多對多）、`DemandTagCategory`（需求↔標籤多對多），都掛在 `CategoryType.CompanyTag`／對應的 Demand 版本上，支援階層。**這塊資料表跟業務邏輯都已經有了**，前端只是還沒把「智慧技術」那個 5 頁籤巢狀 UI 接上真正的標籤 API。
- **供給端「卓越／新興」的文件區分邏輯，其實後端已經預留了**：`DocumentType` enum 裡 `TechnicalCapability`／`CloudMarketplace`／`DigitalServiceCapability`／`Application` 這 4 種文件互斥（四選一），對應規劃書「卓越會員：技術服務能量登錄/雲市集/數位服務機構登錄」vs「新興會員：登錄申請書」的分流邏輯——選前三種其一＝卓越，選第四種＝新興，這個分流的資料結構已經在，只是還沒看到根據「選了哪種文件」自動判斷會員等級的程式碼（下面會列成業務邏輯缺口）。

## 🔴 後端缺少：資料表

| 缺少的欄位/表 | 對應規劃書需求 | 目前狀況 |
| --- | --- | --- |
| `Member` 缺少「所屬公司名稱」「產業別」自由文字欄位 | 個人會員申請只需要「有效電子郵件帳號、所屬公司名稱及產業別」，**不需要真的建立一筆 `Company`** | `Member.CompanyId` 是選填的（設計上支援個人會員不掛公司），但完全沒有對應的自由文字欄位存這兩項基本資料——個人會員填了這兩欄，資料要存去哪裡目前沒有位置 |
| `DocumentType` 缺少「工廠登記證明文件」 | 需求端申請要交的是**工廠登記證明文件**，跟供給端/需求端共用的「公司登記證明文件」是不同的法定文件 | 目前 `DocumentType.CompanyRegistration` 註解寫「供給端、需求端共用」，等於需求端也是交公司登記證明，跟規劃書條文（工廠登記證明）對不上，需要新增一個列舉值或確認是否為同一份文件 |
| 會員/企業「停權期限」欄位 | 「經取消會員資格者，於兩年內不得重新申請」 | `Status` enum 有 `Suspended`/`Rejected` 這些狀態，但沒有存「禁止重新申請到什麼時候」的日期欄位，目前資料結構擋不住「兩年內不得重新申請」這條規則 |
| 會員資料「上次盤點/下次盤點」時間欄位 | 「執行單位將定期（例如每半年）進行會員資料盤點」 | `Company`／`Member` 都沒有 `LastReviewedAt`／`NextReviewDueAt` 這類欄位，沒有資料可以驅動「半年提醒」這個排程 |
| `Scoring` 表欄位過於單薄 | 新興會員審查要對 6 項標準（人力資源20%、團隊學經歷20%、相關經驗20%、財務制度10%、產品實績20%、財務狀況10%）分別評分 | 目前 `Scoring` 只有單一 `Score` 欄位（一個委員對一份文件/公司只能給一個總分），沒有拆成 6 個子項分數，也沒有記錄「這是哪一項標準」，無法照規劃書的加權配分方式計算 |
| 審查委員名單/委任表 | 「執行單位邀請相關領域學者專家...至少 5 位，共同進行文件資料審查」 | 找不到任何 Entity 代表「這件申請案指派了哪幾位委員」——`MemberApplication.ReviewerId` 是單一 `Guid?`，是內部審核人員（`User`），不是外部學者專家委員，也不支援多人 |
| 電子報公開訂閱名單 | 「透過訂閱名單定期寄送」電子報，且首頁有訂閱入口 | `EmailCampaign`／`EmailCampaignRecipient` 看起來是後台建立好收件人名單後寄送用的，沒看到一張「訪客自行訂閱、儲存 email＋退訂狀態」的表 |

## 🔴 後端缺少：業務邏輯

1. **最大缺口：新興會員「委員評分審查」機制完全沒有實作。** 追過 `Scoring` 在 `SPS.Application` 裡唯一被引用的地方，是刪除公司時順便刪掉關聯的評分紀錄（`CompanyService.cs:730`），**沒有任何程式碼會建立、彙總或判定 Scoring**。`AdminApplicationsController` 只有 `/claim`（單一人員認領）跟 `/review`（單一人員核准/拒絕）兩個端點，是「一位內部審核員決定通過或拒絕」的單軌流程，跟規劃書要求的「至少 5 位外部學者專家各自評分、委員半數以上給 70 分以上才合格」完全是兩套機制。這塊需要重新設計：委員指派、各自獨立評分（6 項加權標準）、自動彙總判定合格與否。
2. **供給端「卓越／新興」自動分流沒看到對應邏輯。** `DocumentType` 資料結構雖然預留了四選一，但沒找到「申請人選了哪種文件 → 系統自動判定卓越或新興、走哪條審查路徑」的程式碼——目前看起來這個判斷可能還是要人工看，不是系統自動分流。
3. **「兩年內不得重新申請」的黑名單檢查沒有實作**——沒有找到任何 `CreateApplication`/`Register` 流程裡去檢查「這個統編/email 是否還在停權期間」的邏輯，配合前面提到缺少的停權期限欄位，這條規則目前完全擋不住。
4. **會員資料半年盤點提醒沒有排程機制**——沒找到對應的排程工作（cron/背景工作）。
5. **供給端動態管理「優先曝光」機制沒看到**——規劃書提到「積極提供產業案例、參與輔導或媒合作業...得提供優先案例曝光（電子報、首頁）」，沒找到對應的排序權重或標記欄位/邏輯。
6. **個人會員升級企業會員的「升級」流程**——規劃書明確這是既有個人會員的獨立升級路徑，需要確認後端是否有「從既有 Member 建立/關聯 MemberApplication」的專屬邏輯，還是跟全新申請走同一套（如果走同一套，個人會員升級時應該不需要再填一次帳號資訊，只需要補企業資料）。目前沒有看到明確區分。

## 📌 建議下一步

1. **先跟業主/PM 確認「新興會員委員評分」這塊的優先順序**——這是目前發現落差最大、影響範圍最廣的一塊（資料表、業務邏輯、端點、前端都要動），如果今年執行期程內就要上線，建議儘早排時程；如果暫緩，先讓新興會員走人工線下審查、系統只做單軌通過/拒絕也是一個過渡方案，但要跟業主明確溝通「系統目前做不到規劃書寫的評分機制」。
2. **會員註冊精靈重新設計方向**：拆成三段（個人會員簡易註冊 → 企業會員申請書+聯絡人清單 → 審核通過後補公司主檔資料+標籤），不要照舊站那份 p01~p03.html 的一頁式大表單繼續做下去。
3. **「我要媒合」「計畫簡介」「訂閱電子報」這三塊前端頁面**，後端支撐度不同：媒合已經有 API 可以直接接、計畫簡介可能可以沿用既有 CMS 模組、電子報訂閱則連端點都要先請後端補。
4. 其餘資料表缺口（工廠登記文件類型、停權期限欄位、盤點時間欄位）都是小改動，可以跟後端一次性排進一個 sprint 補齊。
