# 會員收件匣規劃

> **實作狀態（2026-10-12）：第一階段（系統通知收件匣）已寫好並推到 main，尚未部署與實測；第二、三階段未開始。**

2026-10-12 同事提出：希望會員有「收件匣」，可以**收到系統回覆**，也能**傳訊息**。產品方確認：傳訊息「兩種都要」（傳給平台客服、會員之間互傳）；系統回覆要涵蓋下列四類。目前前台**沒有任何站內通知**，只有寄信（且測試機的寄信功能是關的），買方（需求業者）收到的供應業者回應只能從信箱看。

## 一、現況（盤點）

| 項目 | 現況 |
|---|---|
| 會員↔客服、會員↔會員聊天 | **後端已有**：`MemberChatController`（`api/member-chat`：建立會員對會員聊天 `create`、建立客服聊天 `create-admin`、聊天列表、訊息歷史、未讀數），後台 `AdminMemberChatController`（領取、離開、等待清單），即時通訊用 SignalR（`/hubs/customer`）。前台 `SPS.Web` **只有型別（`types/member-chat.ts`），沒有任何畫面** |
| 系統通知 | 資料表 `Notification` 與 `NotificationController` 存在，但 `recipient` 只是自由字串、沒有擁有者概念，前後台都沒有頁面用它；**會員沒有通知收件匣** |
| 寄信 | 有：媒合通知、審核通過／退回等，皆為 email |

## 二、系統回覆要涵蓋的內容

1. **回應審核結果**：供應業者的回應通過或退回（含退回原因）。
2. **收到的回應**：需求業者（刊登者與追蹤者）收到審核通過的供應業者回應。解決「買方只能看信箱」。
3. **新需求媒合通知**：後台發布需求時，符合標籤門檻的供應業者收到通知。
4. **客服對詢問單的回覆**：承辦人處理詢問單後的回覆。**目前系統不代寄，要新增後台「回覆」功能**（只有登入會員送出的詢問單才有收件對象，匿名詢問單沒有）。

## 三、分階段實作建議

**第一階段：系統通知收件匣（上面四類）**
- 後端：新增會員通知資料表（擁有者＝會員、類型、標題、內容、連結、已讀、建立時間）；在上述四個事件發生處寫入通知（寄信照舊，兩邊都有）；API：列表、未讀數、標記已讀、全部已讀。
- 後台：詢問單詳情新增「回覆會員」（寫入通知，並可選擇同時寄信）。
- 前台：頁首「收件匣」圖示與未讀數、會員中心新增「收件匣」分頁（通知列表、點開看連結、標已讀）。

**第二階段：會員↔客服訊息畫面**
- 前台做聊天畫面（客服對話列表、訊息、送出、未讀數），接現有 `create-admin`、訊息歷史與 SignalR。後台聊天頁已存在。

**第三階段：會員↔會員訊息（需要先決定規則，見下）**
- 後端聊天已有，前台沿用第二階段的畫面；但要補規則與保護機制。

## 四、第三階段要先決定的事（尚未確認）

- **誰可以傳給誰？** 例如只限「需求端與供給端」之間，或只有在供應業者的回應通過之後，才允許對該需求的刊登者／回應者開啟對話。
- **與「回應要審核」的關係**：目前供應業者對需求的回應必須經後台審核才會寄出；若會員之間可以直接傳訊息，等於繞過審核。要不要讓訊息也先審核，或只開放在已通過的回應之後。
- **保護機制**：封鎖、檢舉、頻率限制、訊息長度與附件、後台能否查看對話（隱私與稽核的取捨）。
- **個人會員**能否參與（目前媒合功能只開放企業會員）。
- 聯絡資訊（電話、信箱）在對話中的處理。

## 五、已知的相關缺口

- 買方（需求業者）目前看不到收到的回應，只能靠信箱（`後續更新需注意事項.md`）。第一階段的「收到的回應」通知可以解決。
- 測試機的寄信功能是關的，通知信都不會寄出；站內收件匣上線後，這台至少看得到通知。
