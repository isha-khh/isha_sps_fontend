## A. 上線前（備份與確認）

- [ ] **備份資料庫。** API 啟動時會自動套用所有待執行的 migration（`Program.cs`，所有環境都會，沒有開關），部署新版 API 的那一刻就會改資料庫，不用另外跑遷移指令。
- [ ] **確認要套用的 migration**（自 2026-10-01 起，共 6 個，依序執行）：

  | Migration | 對資料的影響 |
  |---|---|
  | `AddMemberSystemPhase1` | `Company.Level` 重新對應：舊 Standard(1)→Standard(0)、Premium(2)→Excellent(1)、VIP(3)→Emerging(2)；舊 Basic(0) 本來就等於新 Standard(0)。`MemberApplication.ApplicantType` 的 0 回填成 Company(2)。新增評分（`Scorings`）、申請人類型、既有會員、會員公司名稱／產業別等欄位 |
  | `AddIndustryToMemberApplication` | 新增欄位 |
  | `AddBannerSchedulingAndHeroFields` | Banner 新增上下架時間、首頁主視覺文案欄位；**既有 Banner 的 `Published` 預設為 true**；種入版位 `home-hero`、`news-top` |
  | `AddSiteBannerPositions` | 種入 10 個版位：`sidebar-news`／`serve`／`talent`／`tutoring`／`promotion`／`matching`／`support`、`sidebar-support-tutoring`、`talent-top`、`support-top`（已存在就略過） |

  | `AddApplicationAccessKey` | `MemberApplication` 新增 `AccessKeyHash` |

- [ ] **盤點資料庫裡的後台帳號與角色**（上線後的權限行為會變，見 C 節）：
  - 有哪些後台使用者**沒有任何角色**？他們以前只要登入就能呼叫大部分後台 API，上線後幾乎全部 403。
  - 現有角色名稱是否和範本角色同名（`超級管理員`、`內容編輯`、`審核員`、`客服`、`行銷人員`）？同名的不會被覆蓋，但權限不會是範本的內容。
  - 正式環境若存在 `Company.Level` 的實際資料，確認上表的對應結果符合預期（Phase 1 的 `Down` 無法還原原本的 Basic／Standard 差別，回滾後一律變舊 Standard）。
- [ ] **部署順序：API 先、前台與後台前端後。** 新前端依賴新 API（申請存取密鑰 cookie、補寄、進度查詢、Banner 新版位）；新 API 搭舊前端則是申請流程會壞（舊前端不會轉傳密鑰 cookie，完成頁讀不到資料）。三者最好同一個維護時段一起上。

## B. 上線時要設定／確認的環境設定

- [ ] `Bounce_Webhook__Secret`（至少 16 字元）：**只有**外部郵件伺服器會呼叫 `POST /api/Log/mail/bounce` 時才需要。沒設定時這個端點停用（回 503），不影響其他功能。設定後呼叫端要帶標頭 `X-Webhook-Secret`，兩邊密鑰一致。目前 repo 內找不到任何呼叫它的程式，實際的退信處理走 IMAP。
- [ ] `App__BaseUrl`：郵件裡的「申請進度查詢」「登入」「重設密碼」連結都用它組（`{BaseUrl}/member/register/status?...`）。**必須是前台公開網址且含站台路徑**（前台 `basePath` 是 `/sps`，所以正式環境若掛在 `/sps` 底下就要寫 `https://主機/sps`）。上線後寄一封測試信點連結確認不會 404（目前本機環境的設定是 `https://sdd.nat.gov.tw/sps`，連結都長 `{BaseUrl}/member/reset-password?token=…`，代表前台掛在 `/sps` 底下）。
- [ ] `CORS_Setting__WithOrigins`：要包含前台與後台的正式網址，且需允許帶 cookie。後台請求新增了自訂標頭 `X-Admin-Client`（後端 CORS 已設 `AllowAnyHeader`，若前面的 nginx／WAF 有自己限制標頭白名單要加）。
- [ ] **前台與 API 必須讓 cookie 通用**（同一個主機名，透過 nginx 分路徑）。申請存取密鑰 cookie `appkey_{id}` 和登入 cookie 一樣由 API 設定，前台完成頁（Server Component）要從收到的請求讀出它再轉傳給 API。若前台與 API 是不同主機名（例如 `www.x.com` 與 `api.x.com`），完成頁會讀不到 cookie 而顯示「找不到申請資料」。登入 cookie 本來就有同樣的前提，所以多半沒問題，但請實測一次完整申請流程。
- [ ] cookie 的 `Secure`／`SameSite` 來自資料庫的「HTTP 安全設定」（系統設定→安全設置），申請存取密鑰 cookie 沿用同一份設定。
- [ ] SMTP：「系統設定→郵件」要是啟用狀態且設定正確。補寄功能會在郵件服務停用時明確回報「沒寄出」。

## C. 上線後立刻要做的事

- [ ] **前台會員 token 的權限 claim 已改名**（`Permissions` → `MemberPermissions`）。上線前簽發的會員 token 在有效期內仍帶舊名稱，後端有**過渡期相容**（只對「有 MemberId、沒有 Admin 角色」的 token 退回讀舊名稱），所以會員不用重新登入。**等舊 token 全部過期後**（至少一個 `JWT_Setting__Expires` 週期，compose 預設 1440 分鐘；refresh 會重簽成新名稱）可以刪掉 `UserPermissionClaims.GetMemberPermissions` 裡「過渡期：舊 token」那個分支，建議上線滿 7 天（refresh token 有效期）後移除。
- [ ] **請所有後台使用者重新登入。** 權限寫在 token 裡：舊 token 帶的是舊權限位元，在 token 到期前（`JWT_Setting__Expires`，compose 預設 1440 分鐘）看不到新權限（例如新拆出的「橫幅管理」「網站內容」）。最快的方式是通知大家登出再登入。
- [ ] **檢查 5 個範本角色與既有角色的權限內容**（後台→系統管理→角色管理）。migration 依「原本能做什麼」自動補了新權限，讓行為不變：
  - 舊的全權限角色 → 補上全部新旗標
  - 有 `ManageUsers`／`ManageSettings` → `ViewActionLogs`；有 `ManageSettings`／`ManageNews` → `ManageFiles`
  - 有 `ManageMembers`／`ManageCompanies`／`ManageProducts` → `ExportData`
  - 有 `ManageNews` → `ManageBanners`、`ManageSiteContent`、`ManageMedia`
  - 有 `CustomerService`／`SendBulkEmail` → `ViewMembers`、`ViewCompanies`
  
  補完請人工看一遍有沒有人拿到不該有的權限，或少了該有的。
- [ ] **信件範本加上進度查詢連結。** 信件範本存在資料庫，程式裡預設範本的更新**不會**蓋掉已存進去的內容。到「系統設定→信件範本」，在「申請提交確認」「申請通過」「申請拒絕」三封信裡加上：
  `<a href='{{statusUrl}}'>申請進度查詢</a>`（變數 `statusUrl` 三封信都已傳入，不加只是不顯示）。
- [ ] **到「系統設定→驗證碼」開啟 `forgot-password` 場景。** 目前資料庫裡這個場景是**關閉**的，忘記密碼端點等於沒有驗證碼；後端另外有「同信箱 1 分鐘只寄一次、同 IP 15 分鐘最多 10 次」的限制擋著，但開啟驗證碼才是完整的防護（前台表單會依設定自動顯示／隱藏驗證碼欄位）。
- [ ] **設定前台頁尾連結**（後台「內容管理 → 頁尾連結」，需要「網站內容管理」權限）：功能專區、LINE／Facebook／Instagram／YouTube／Threads／Podcast、無障礙標章 2.0、工業安全衛生協會的網址。**沒填的項目前台不顯示**（以前是點了只會回頁首的 `#`），所以上線前沒設定的話，頁尾不會有社群圖示。經濟部產業發展署預設是 `https://www.ida.gov.tw/`。同一頁還可以改頁尾的聯絡資訊（地址、地圖連結、電話、信箱），預設值就是原本寫死的內容，沒改過看起來不變；欄位清空＝前台不顯示那一列。前台頁尾快取 5 分鐘，儲存後最多 5 分鐘才看得到。網址只接受 http／https（功能專區另外可填 `/` 開頭的站內路徑）。
- [ ] **頁尾「瀏覽」數字**現在是真的累計人次（`GET /api/site-counter` 的 `totalVisitors`；以前是寫死的 10,781）。前台每次換頁會呼叫 `POST /api/site-counter/visit`，「新訪客」以瀏覽器 localStorage 判斷。**要校正起始數字**（例如沿用舊站的累計）到後台「內容管理 → 頁尾連結」最下面的「瀏覽人次」卡片（需要「網站內容管理」權限；只填要改的欄位）。後端防灌水：同 IP 每分鐘最多累計 60 次、同 IP 24 小時只認一次新訪客、後台使用者瀏覽不算。頁尾數字快取 60 秒。
- [ ] **設定「我要投稿」頁**（後台「內容管理 → 頁面設定」，需要「網站內容管理」權限）：上傳或挑選三個投稿格式檔——**Word（.docx）**、**ODF（.odt）**與 **PDF（.pdf）**；副檔名必須對得上，後端也會檢查，且不能選資料夾或會員申請附件。前台「下載投稿格式」按鈕會開對話框列出已設定的格式；**三個都沒設定時前台顯示「投稿格式準備中」**，所以上線前沒設定的話這個按鈕是停用狀態。同一頁可設定投稿聯絡人／電話／信箱（原本寫死、聯絡人還是示範用的「王小名」；現在聯絡人預設留空＝不顯示，電話與信箱預設為原本的值）。檔案被刪除時前台會自動不顯示那個格式。前台快取 60 秒。
  - **也可以隨程式碼 seed（不用進後台上傳）**：目前已放在 `src/SPS.Api/wwwroot/seed/contribute/`：`contribute-template.docx`、`.odt`、`.pdf`（各一個）。**磁碟上的檔名刻意用英文**（避開中文檔名在不同作業系統、Docker、網址上的編碼風險）；使用者下載到的檔名由程式統一設成「電子報投稿格式.docx／.odt／.pdf」（`ContributeFormatSeeder.DisplayName`），要改名稱改那個常數。檔案會隨 API 一起發佈，啟動時自動登錄成靜態檔案並套用到頁面設定。規則：**這個版本的檔案還沒 seed 過 → 套用；已經 seed 過 → 不動**（以檔案內容雜湊判斷）。所以管理員在後台改選別的檔案或移除格式後，重啟不會被改回來；之後把新版範本用同檔名換進這個資料夾再部署，才會自動更新成新版（連同被丟進回收桶的舊版也會恢復）。這個資料夾裡不要放其他檔案，所有 `wwwroot` 底下的檔案都會被掃描並公開在檔案管理（以 `.` 開頭的隱藏檔如 `.DS_Store`、`.gitkeep` 與 `Thumbs.db` 會被略過）。
- [ ] **設定「下載資源」**（後台「內容管理 → 頁面設定」最下面的「下載資源」區塊，需要「網站內容管理」權限）：前台其他地方的下載按鈕都集中在這裡維護，共 11 個固定項目——會員註冊的《會員申請須知》與附件一（個資同意書）、附件二（登錄申請書）、附件三（審查評定方式）；補助專區 `/support` 五個快速連結（補助懶人包、申請須知、計畫書格式、線上申請說明、常見問答）；人才培訓 XR 的「下載 XR 訓練模組」；以及補助專區右側欄的「申請入口」按鈕（只能設外部連結，**沒設定就整顆不顯示**）。每個項目可選 Word／ODF／PDF 檔案（只列該項目允許的格式），或填**外部連結**；**有填外部連結就優先使用連結**（前台開新分頁），沒有就依檔案：只有一個格式直接下載、多個格式跳對話框讓使用者選、都沒有顯示「準備中」。外部連結只接受 http／https。前台快取 60 秒。
  - **上線前一定要做：** `talent-xr`（XR 訓練模組）**沒有 seed 檔案，只能設外部連結**，不設的話前台按鈕是停用的「下載連結準備中」；`support-apply-entry`（申請入口）也一樣只能設外部連結（填補助申請系統的網址）。
  - **其餘 9 項（`talent-xr`、`support-apply-entry` 以外）已隨程式碼 seed**（放在 `src/SPS.Api/wwwroot/seed/register/`、`seed/support/`，磁碟上用英文檔名，使用者看到的中文檔名由 `DownloadResourceCatalog`（`SPS.Application/DTOs/SystemSettings/DownloadResourcesDto.cs`）的 `DisplayName` 決定；seed 規則與投稿格式相同：同一份內容只套用一次，管理員在後台改選或移除不會被重啟蓋掉，換新版檔案同檔名再部署才會更新）。附件二（登錄申請書）的 Word、ODF、PDF 三種格式都已 seed（Word 版 2026-10-06 補上）。
  - **新增下載項目**（要改程式）：在 `DownloadResourceCatalog.Slots` 加一筆（Key、群組、標題、使用位置、允許的副檔名、seed 檔名與中文顯示名），前台用 `fetchDownloadResources()` 取得後以 `<DownloadDialog links={downloads[key]?.links ?? []} …>` 渲染。後台畫面會自動出現新項目。
- [ ] **為新版位上傳 Banner。** 前台各頁面原本寫死的假廣告／假輪播已全部拿掉，沒有設定 Banner 的版位就**整塊不顯示**（側欄、輪播都是）。到「內容管理→橫幅管理」依版位建立。首頁主視覺沒設定會退回內建內容。
- [ ] **處理「未指定版位」的舊 Banner**（本機的 "banner2"、"111" 這種）。它們不會顯示在前台；後台列表會顯示黃色警示標籤。現在上架中的 Banner **一定要選版位**才能存，編輯舊 Banner 時要先選版位或取消上架。
- [ ] **密碼重置連結行為變了**：重置連結現在**只能用一次**（以前同一個連結在 30 分鐘內可以重複重設多次，後台與前台會員都一樣）。上線前已寄出、還沒用的連結會失效，使用者重新按「忘記密碼」即可。
- [ ] **通知客服／審核同仁的行為變化**：
  - 上線前建立、尚未送出的**申請草稿**，申請人不能再開啟（舊資料沒有存取密鑰），需要重新填寫。審核與已送出的申請走後台，不受影響。
  - 申請人現在可以到 `/member/register/status` 用「申請編號＋信箱」或「信箱＋聯絡電話」查審核進度；信箱故障時後台可在申請詳情「補寄通知信」，必要時更正信箱（先打電話確認本人）。

## D. 上線後驗證（建議逐項做）

用一般瀏覽器與後台各走一遍，或用 curl：

- [ ] 前台首頁、`/news`、`/news/{id}`、`/search?q=…`、`/faq` 都能開；公告詳情頁開啟後該公告瀏覽數 +1（同一 IP 30 分鐘內不重複計）。
- [ ] 會員 token 打後台 API 要回 403：例如 `GET /api/admin/members`、`GET /api/Log/action`、`POST /api/export/members`。
- [ ] 匿名打 `GET /api/News?PageSize=100` 沒有任何 `published=false` 的項目；`SuccessCase`、`Demand`、`Album` 同理。
- [ ] 匿名打 `GET /api/Company/{id}`，回應裡 `charge`、`chargeEmail`、`chargePhone`、`chargeMobile`、`remark`、`designatedContacts` 都是 null。
- [ ] 完整走一次會員註冊：建立 → 上傳附件 → 完成頁顯示申請資料（驗證 cookie 轉傳）→ 送出 → 收到確認信 → 用編號＋信箱查得到。
- [ ] 後台用審核員帳號審核一筆申請；用只有「檢視申請」的帳號確認看得到但不能審核、不能補寄。
- [ ] 後台補寄通知信：寄到原信箱成功；更正信箱成功後，用新信箱可查到、舊信箱查不到；1 分鐘內再寄會被擋。
- [ ] 申請附件的下載網址 `/api/FileManagement/{id}/download`：匿名回 404，後台有「檢視申請」權限的人可下載；網站上的圖片（公告、Banner）仍可正常顯示。
- [ ] 密碼找回完整走一次：`/member/forgot` 送出 → 收到信 → 點信中連結開啟 `/member/reset-password`（**確認連結的網址不會 404**，也就是 `App__BaseUrl` 含 `/sps`）→ 設定新密碼 → 用新密碼登入、舊密碼不能登入 → 同一個連結再點顯示「無效或已過期」。後台使用者的忘記密碼同理。
- [ ] 後台各選單依權限顯示正確；用「內容編輯」角色登入，能編公告、橫幅、上傳圖片，但進不了會員管理、系統設定。
- [ ] 後台「橫幅管理」的瀏覽次數、點擊次數開始增加（前台頁面載入時會送曝光，點擊廣告會送點擊）。
- [ ] 前台右下角（768–1399px 寬度）出現懸浮搜尋按鈕；≥1400px 為 header 圖示；手機版為選單內輸入框。

## E. 回滾注意

- 回滾程式碼但不回滾資料庫通常可行（新增的欄位與版位不影響舊程式），**但**：`Roles.Permissions` 已被改寫（舊程式看得懂，只是多了它不認得的位元，無害）；舊前端搭新 API 的申請流程會壞（見 A 節）。
- 要回滾 migration 用 `dotnet ef database update <上一個 migration>`；`UpgradeAdminPermissionsToRbac` 的 `Down` 會清掉新旗標位元，範本角色沒有人指派才會刪；`AddMemberSystemPhase1` 的 `Down` 無法還原 Basic／Standard 的差別。
- **回滾前一定要先備份**，Down 沒辦法救回已經被改過的資料。

## F. 之後改程式的規則

### 後端 API 的權限（最容易出事）

1. **後台專用端點一律兩層**：`[Authorize(Roles = "Admin")]`（是不是後台使用者）＋ `[RequirePermission(UserPermission.X)]`（有沒有這項權限）。**不要只寫裸的 `[Authorize]`**：會員 token 也過得去。
2. **後台與會員的權限 claim 名稱不同**：後台 `Permissions`（`UserPermission` 位元）、會員 `MemberPermissions`（`MemberPermission` 位元），常數在 `SPS.Domain/Constants/AuthClaimTypes.cs`。兩個列舉的位元意義互不相干（會員的 `ViewCompany` = bit0 = 後台的 `ManageUsers`），**不要直接 `FindFirst("Permissions")`**：後台用 `User.GetAdminPermissions()`、會員用 `User.GetMemberPermissions()`，兩者都會先確認身分（後台要 Admin 角色；會員要有 MemberId 且沒有 Admin 角色）。新增讀取權限的程式碼一律走這兩個方法。
3. **`[AllowAnonymous]` 擋不住 `IAuthorizationFilter` 型的屬性**（`RequirePermission` 就是）。在同一個 controller 同時有匿名與受保護的 action 時，不要把 `RequirePermission` 放在 class 上，放在各 action（例如 `SystemInfo` 的 `health`、`FileManagement` 的 `download`）。
4. **公開的 GET 列表／詳情要強制只回已發布**：非 Admin 呼叫時覆寫 `Published = true`，詳情對草稿回 404。新增有「發布／上架」狀態的內容類型時照做。
5. **匿名可呼叫的 DTO 不要帶內部欄位**：負責人聯絡資料、備註、營收、窗口名單、審核員備註這類，非 Admin 要清掉（見 `CompanyController.HideInternalFields`）。
6. **匿名端點要有第二因子與限流**：申請編號可以猜，所以進度查詢要信箱／電話、並限制失敗次數；webhook 要有共享密鑰。申請資料的讀寫靠 `appkey_{id}` cookie，不是 GUID。
7. **授權上限**：建立／修改角色、指派角色只能給自己也擁有的權限（`CanGrant`）。新增任何「授予權限」的功能都要套用。
8. **前後台共用的路徑**（`/api/News`、`/api/Banner` 這類）靠 AdminWeb 帶的 `X-Admin-Client` 標頭，讓後端優先採用 `adminAccessToken`。新增後台 API client 時沿用 `lib/api-client.ts` 的 axios 實例。

### 密碼重置與一次性連結

- 重置令牌（JWT）簽發時把「當時密碼雜湊的指紋」（`PwdStamp`，`PasswordStamp.Compute`）寫進去，驗證時與目前密碼雜湊比對（`PasswordStamp.Matches`）：密碼一改（用這個連結重設、或之後自己改）所有舊連結一起失效，不需要另外存「已使用的令牌」。沒有指紋的舊令牌一律視為無效。**之後如果新增其他「寄連結讓人改密碼／登入」的流程，照這個做法，不要只靠效期。**
- 匿名且會「替任意信箱寄信」的端點（忘記密碼、發驗證碼…）一定要有限流與冷卻，不能只靠驗證碼（驗證碼場景可能被關掉）。同信箱冷卻期間也要回成功，不要洩漏這個信箱有沒有註冊。

### 新增或調整權限旗標（`UserPermission`）

- 位元**不可重用、不可改號**（已存在資料庫），**不可超過 bit 52**（API 回傳的 JSON 數字超過 2^53 會失去精度）。
- 新旗標要同步更新四處：`UserPermission.All`、`AdminRoleService.GetAllPermissions`、AdminWeb `lib/permissions.ts`（含 `expandPermissions`）、AdminWeb `AdminLayout.tsx` 的選單權限；並寫 migration 決定現有角色要不要自動補上，否則上線後沒人有這項權限。
- 「維護包含檢視」的規則在後端 `Expand()` 與前端 `expandPermissions()`，改一邊一定要改另一邊。
- 角色權限改動後，使用者要重新登入才生效（權限寫在 token）。

### Migration

- 手寫的 SQL 要用**實際的資料表名稱**（例如是 `UserRole` 不是 `UserRoles`、`Company` 不是 `Companies`），並且**實際跑一次 `Down`**——這次就是靠回滾測試才抓到表名寫錯。
- 純資料的 migration 用 `dotnet ef migrations add` 產生空殼後手寫 `Up`／`Down`，種資料要用 `WHERE NOT EXISTS` 讓重跑安全。
- 因為啟動時自動套用，**新增 migration 的版本一發佈就會改正式資料庫**；有資料轉換的務必先在測試環境用正式資料備份演練。

### 信件

- 信件範本以資料庫為準，程式裡的預設值只在資料庫沒有該範本時才用。**改了預設範本或新增變數，要同步到後台信件範本**。
- `EmailService.SendEmailAsync` 在郵件服務停用時會**靜默略過、不丟例外**。需要確實告知使用者「有沒有寄出」的功能，要先呼叫 `IsEnabledAsync()`。
- 寄信失敗不應該影響主流程的地方（申請提交、審核）已經包 try/catch；補寄這種「寄信就是主要目的」的功能則要把失敗回報給操作者。

### 前台（SPS.Web）

- API 回傳欄位名稱以 `url`／`uri` 結尾且以 `/` 開頭的值，axios 攔截器會自動加上 basePath，搭配 `next/link` 會變成 `/sps/sps/…`。這類欄位要在 `lib/api.server.ts` 用 `stripBasePath` 處理。
- Server Component 呼叫需要瀏覽器 cookie 的 API（例如申請存取密鑰）時，cookie 不會自動帶，要用 `cookies()` 讀出再手動轉傳。
- 計數類 API（瀏覽數、曝光、點擊）用 `fetch(..., { keepalive: true })`，不要用 axios：axios 送 POST 前會先等 CSRF token，遇到整頁跳轉的點擊會在送出前就被中止。
- Banner 沒有設定時各處都是「整塊不顯示」，不要再放回假資料。
- 舊站 CSS 會改掉一些全域元素的外觀：許多頁面的 `<a>` 文字預設是白色（原本放在深色按鈕上）、`.btn-close` 是把「X」文字畫成圓鈕。在白底的元件（例如對話框）裡放連結或關閉鈕時，要自己指定文字顏色、並在關閉鈕裡放 `X` 文字，否則會整行字看不見。
- **靜態檔案（`wwwroot`）**：啟動時 `StaticFileScannerService` 會把 `wwwroot` 底下所有檔案登錄成公開的靜態檔案；同路徑的檔案內容換了（雜湊不同）會更新資料庫的大小與雜湊，已被刪除的紀錄也會恢復。要 seed 內容時，照 `ContributeFormatSeeder` 的做法：掃描完才 seed、用內容雜湊標記「已套用的版本」，不要每次啟動都蓋掉管理員在後台的調整。
- **`ASPNETCORE_WEBROOT` 指到別的目錄時（目前正式機就是）**：部署機的 compose 把 WebRoot 設成掛載進容器的主機目錄（`/home/shareproject/SPS`），而不是映像裡的 `/app/wwwroot`，所以靜態檔案掃描掃的是主機目錄，映像裡的 `wwwroot/seed` 掃不到、seed 就不會套用（現象：下載資源全是「準備中」、投稿頁「投稿格式準備中」，log 也沒有任何 seed 訊息）。`StaticFileScannerService.SyncSeedFiles` 現在會在掃描前，把應用程式內建的 `wwwroot/seed` 複製到實際的 `WebRoot/seed`（只複製缺少或內容不同的檔案）。注意這個目錄會被掃描並公開在檔案管理，**WebRoot 不要指到含原始碼、.env、設定檔的目錄**。
- 檔案管理的「文件」分類（`FileRepository`）要包含 ODF（`.odt／.ods／.odp`），否則後台選檔對話框的「文件」篩選看不到 `.odt`。
