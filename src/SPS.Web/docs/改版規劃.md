## 前端欄位設計確認清單（持續更新）

先把「前端這幾張卡片/頁面實際用到哪些資料欄位」定案下來，之後要
擴充後端／串外部服務（Google Maps 之類）再一併處理，不要邊確認
邊改，來回浪費工。目前 `/news` 列表卡片（[NewsListCard.tsx](../src/components/news/NewsListCard.tsx)）
確認過的欄位：

| 畫面位置 | 欄位 | 資料來源 | 狀態 |
|---|---|---|---|
| 卡片左側縮圖 | 封面圖 | `News.Picture.DefaultImageUri` | ✅ 已接 |
| 標題列上方（紫色）**公告類型標籤** | `categoryName` | `Category` 資料表（分類，跟 FAQ 的分類是同一套機制） | ✅ 已接 |
| 標題列上方 日期 | `startDate` | `News.StartDate` | ✅ 已接（`startDate` 可能是 `null`、格式要處理，見下方「真資料曝光的顯示問題」） |
| 標題列上方（外框）狀態小標籤（活動進行中／已結束） | 前台算出來的，不是存的欄位 | 用 `News.StartDate`／`EndDate` 跟現在時間比對，見下方「狀態標籤」小節 | ✅ 已接 |
| 摘要文字 | `introduction` | `News.Introduction` | 🟢 欄位存在，這篇資料沒填（AI 輔助生成是後續想法，見下方） |
| 📅／📍 時間地點條列 | 目前沒有 | 見下方「地點」小節 | ❌ 改版項目，本次不做 |
| 標題下方（藍色）**內容標籤**（產業AI／技術文件） | `tags` | `Tag`／`EntityTag`（這篇公告自己的關鍵字，跟上面的分類標籤是不同機制，不要混在一起） | 🟡 API 已接，但後台編輯器沒有能設定標籤的欄位，見下方「內容標籤：後台缺編輯功能」 |

**這兩層標籤刻意分兩種資料來源、不能合併**：上面紫色是「這篇屬於
哪個分類」（`Category`，一篇公告通常只屬於一個分類），下面藍色是
「這篇有哪些關鍵字」（`Tag`，一篇公告可以掛多個標籤）——兩者語意
不同，UI 上也刻意用不同顏色/位置區分，程式裡也是接兩張不同的表，
之後如果有人想「乾脆都用 Tag 做」或「都用 Category 做」要特別注意
不要合併錯。

地點／Google Maps 那塊**明確歸類為「後續改版項目」**，不在這次
`/news` 資料串接的範圍內，等前端欄位設計全部確認完、要動的時候再
一次處理（含 Google Cloud 帳戶設定、後端 schema、後台編輯器、前台
地圖元件）——詳見下方「待決定：活動的時間／地點」小節，那節的內容
是先寫好、之後真的要做的時候可以直接照著做，不代表現在要動手。

## 2026-09-08：公告列表卡片，假資料 vs 真資料的落差

比對假資料版本（設計稿等級的示範畫面）跟真後端資料版本，同一張卡片
缺了好幾塊東西。逐項拆解性質不一樣：

| 項目 | 性質 | 處理方式 |
|---|---|---|
| 封面圖 | API 沒有欄位（`News` entity 有 `PictureId`/`Picture`，但 DTO 沒帶出來） | ✅ 已擴充，見下方 |
| 狀態標籤（活動進行中） | 後端不用存狀態，用 `EndDate` 有沒有值＋跟現在時間比對，前台自己算 | ✅ 已擴充，見下方 |
| 標題下方關鍵字標籤 | API 沒有欄位（`Tags` 原本只有詳情 API 有，列表沒有） | ✅ 已擴充，見下方 |
| 摘要文字 | 欄位存在，是這篇資料沒填 | 💡 新想法：AI 輔助生成，見下方 |
| 時間/地點條列（📅📍） | 資料庫完全沒有對應欄位，這是「活動類」公告才需要的資訊 | ❓ 待決定，見下方 |

### ✅ 已擴充（2026-09-08 完成）

**後端**（`src/SPS.Application`／`src/SPS.Infrastructure`）：

- `NewsListItemResponse`／`NewsResponse` 新增 `ImageUrl`（來自
  `News.Picture.DefaultImageUri`）、`Tags`（原本只有詳情有）；
  `NewsListItemResponse` 另外新增 `EndDate`。
- `NewsRepository.GetPagedAsync` 補上 `.Include(n => n.Picture)`。
- 新增 `INewsRepository.GetNewsTagsBatchAsync`：列表一頁最多 100 筆，
  逐筆呼叫原本的 `GetNewsTagsAsync` 會是 N+1 查詢，改成一次把整頁的
  Id 丟進 `IN` 子句查完再分組，`NewsService.GetPagedAsync` 已改用這個
  批次方法。

**前台**（`src/SPS.Web`）：

- `lib/types.ts` 的 `NewsItem`／`NewsDetail` 補上 `endDate`／`tags`／
  `imageUrl`（可選，因為舊資料/尚未設定圖片的公告仍可能沒有值）。
- `lib/news-data.ts` 新增 `getNewsActivityStatus(startDate, endDate)`：
  沒有 `endDate` 就不是「活動」類公告、不顯示標籤；有的話依現在時間
  算「即將開始／活動進行中／活動已結束」。**這個判定邏輯的前提是
  2026-09-08 跟後端一起定案的：「是不是活動」不用額外開一個布林欄位，
  有沒有填 `EndDate` 就代表了。**
- `/news`、`/news/[id]` 兩個頁面的封面圖改用 `article.imageUrl`（沒有
  才退回 `NEWS_FALLBACK_IMAGE` 佔位）、列表卡片的關鍵字標籤改用
  `article.tags`、狀態標籤改用 `getNewsActivityStatus()`。

### 🐛 真資料曝光的顯示問題（2026-09-08，已修）

接上真後端資料後實測（截圖比對）發現的兩個顯示問題，都是純前端修正，
不用動後端：

1. **日期顯示成完整 ISO 時間戳記**：畫面直接印出
   `"2026-05-12T00:00:00Z"`，設計稿只要 `"2026-05-12"`。新增
   `formatNewsDate()`（`lib/news-data.ts`）統一處理，`/news`、
   `/news/[id]` 所有顯示日期的地方都改叫這個函式。
2. **`startDate` 為 `null` 時整頁 500**：真後端 `News.StartDate` 是
   可為空欄位，實測 98 筆真資料裡有 2 筆（`id=33`、`id=106`，發布時
   沒填開始日期）確實是 `null`，`formatNewsDate()` 原本直接對字串呼叫
   `.slice()`，沒防 `null`，一開就整頁噴 `TypeError: Cannot read
   properties of null (reading 'slice')`。修正：`lib/types.ts` 的
   `NewsItem.startDate`／`NewsDetail.startDate` 型別老實改成
   `string | null`（如實反映後端 `DateTime?`）；`formatNewsDate()`
   沒有日期時顯示「日期未定」；`getNewsActivityStatus()` 沒有
   `startDate` 就不算活動狀態（顯示錯的狀態比不顯示更糟）。
   **這裡的教訓：後端 DTO 裡任何 `DateTime?`／`?`（可為空）的欄位，
   前台型別都要老實標成可選/可為 null，不能因為多數真實資料有值
   就當作一定有值——這次剛好只有 2/98 筆是 null，比例低到很容易在
   測試時漏測到，之後接其他欄位要留意同樣的陷阱。**

### 🔧 內容標籤：後台缺編輯功能（2026-09-08）

API 端（`Tags`）已經接好，但目前**後台編輯器（`SPS.AdminWeb`）的
公告表單沒有能設定標籤的欄位／UI**，所以就算 API 準備好了，實際
資料庫裡的公告目前幾乎都沒有標籤（拿掉了原本假資料示範用的
「產業AI／技術文件」這種標籤畫面），不是程式没接對，是後台編輯器
這端缺了對應的輸入功能。

要讓「內容標籤」這個設計真的能用，還需要：

- 後台公告表單加一個標籤輸入元件（多選、可能要能新增新標籤，
  參考 `Category`／`CompanyTagCategory` 這套雙路徑標籤機制現有的
  UI 模式，不用重新設計一套）
- 確認要不要開放小編自由輸入新標籤，還是限制在既有標籤清單裡選
  （自由輸入的話，標籤清單會越長越亂，之後可能需要後台再做一個
  「標籤管理」頁面去合併/清理重複或相似的標籤）

這塊不是這次 `/news` 資料串接能解決的（屬於 `SPS.AdminWeb` 的功能
開發，不是 `SPS.Web` 前台的事），先記錄下來，等排後台開發排程時
一併考慮。

### 💡 新想法：AI 輔助生成摘要

後台小編填公告常常不填「摘要」（`Introduction`）欄位——不是欄位設計
有問題，是人懶得寫。想法：**後台編輯器在存檔或另外提供一顆按鈕，
用 AI 把 `Content`（公告內文）餵給 LLM，自動生成一段 100 字左右的
摘要，寫回 `Introduction` 欄位**，小編可以直接用、也可以再手動修改。

這塊還沒有實作規劃，只先記錄想法，之後要展開至少要決定：

- 觸發時機：存檔時如果 `Introduction` 是空的自動生成？還是後台給一顆
  「AI 生成摘要」按鈕，小編自己按？（後者比較不會有「明明想留空卻被
  自動填」的意外）
- 用哪個 LLM／怎麼呼叫：後端直接呼叫某家 LLM API？還是透過現有的
  `ContentEmbedding`（[backend-reuse-audit](backend-reuse-audit-2026-09-07.md)
  提到的 AI 語意媒合功能）同一套 AI 基礎設施擴充？
- 內文是 Puck 區塊 JSON，不是純文字——餵給 LLM 之前要先把 Puck
  `content` 陣列攤平成純文字（跟 `PuckRenderer` 的 legacy-content
  分支處理方向相反，可能可以共用一個「Puck Data → 純文字」的轉換
  函式）。

### ❓ 待決定：活動的時間／地點

假資料版本的「📅 2026.4.15(四)09:00-16:30」「📍 台北國際會議中心101
會議室」這組條列資訊，真後端完全沒有對應欄位——`News` entity 沒有
「地點」這種欄位，這不是漏掉沒吐出來，是 schema 一開始就沒設計這塊。

**2026-09-08 討論後決定：串 Google Places／Geocoding API，做「地址
自動定位」的進階版**（後台輸入地址時自動完成／定位，前台用互動地圖
顯示釘選點，不是只存一段文字地址）。

#### 實測驗證：「活動時間」不是 `StartDate`／`EndDate`，是另一個完全沒結構化的東西

拿真資料 `id=106`（「2026石化產業AI服務說明會」）驗證假資料版本的
📅 那條 meta，發現這條資訊目前**完全沒有對應欄位**，不是只有地點沒有：

```
StartDate: 2026-04-01   EndDate: 2026-09-30   ← 這是「公告上架/開放報名」的期間，長達半年
內文段落裡的純文字："活動時間: 115年4月29日 下午14:00~15:30 (13:30開放報到)"
```

也就是說 `StartDate`／`EndDate` 語意是對的、拿來算「即將開始／進行中／
已結束」狀態標籤沒有錯（見上面「✅ 已擴充」小節）——那是公告本身的
上架週期。但📅那條「活動實際幾月幾號幾點到幾點舉辦」，現在**只是
小編手動打在內文段落裡的一段文字，完全沒有結構化資料**，跟地點是
同一個等級的缺口，不能靠 `StartDate`／`EndDate` 硬湊。

要做的話這塊要另外開欄位（例如 `EventDate`／`EventStartTime`／
`EventEndTime`，或先簡化成一個 `EventSchedule` 文字欄位，只是把
小編本來就會打在內文裡的那句話拉成獨立、可以在列表卡片顯示的
欄位，不強求真的拆成結構化的日期+時間分開存）。跟地點一樣，
**歸在同一個「後續改版」項目裡，這次不動手**，只是先把範圍畫
清楚：「地點」跟「活動實際時間」是兩個各自獨立、目前都沒有欄位
的缺口，不是同一個東西的兩個面向。

#### 欄位設計：地址要拆成「Google 管得到」跟「Google 管不到」兩塊

Google Places／Geocoding 只能定位到**建築物**層級（例如「台北國際
會議中心」這棟樓的地址跟經緯度），樓層／房號這種資訊 Google 完全
沒有資料，沒辦法靠 API 自動生成，這塊只能開一個獨立欄位讓小編手動
填：

| 欄位 | 來源 | 範例 |
|---|---|---|
| `Address` | Google Places Autocomplete 選出來的建築物地址 | 台北市信義區松壽路 3 號 |
| `PlaceId` | Google 回傳的地點 ID，之後要重新查詢/更新這個地點時用這個查，不用整段地址重新配對 | `ChIJ...` |
| `Latitude`／`Longitude` | Google Geocoding 算出的經緯度，前台畫地圖釘選點用 | — |
| `VenueDetail`（樓層/場地細節） | **後台小編手動輸入，不是 Google 給的** | 101 會議室／3樓 A 教室 |

這四個欄位要放在哪裡（直接開在 `News` 上，還是另外開一個可以給
Demand／未來其他內容類型共用的「活動地點」關聯表）還沒定案，要先
確認實際有多少公告是這種「有時間地點的實體活動」——不是所有活動
資訊分類底下的公告都需要地點。

#### 要做的事（分三塊，順序有前後關係）

1. **你這邊要先做**（我沒辦法代勞，牽涉到你自己的 Google 帳戶／
   金流）：
   - 到 Google Cloud Console 建一個專案（或用現有的），**設定
     billing 帳戶**（掛信用卡——沒有 billing 帳戶連 API 都無法啟用，
     即使用量在免費額度內也一樣要先掛）
   - 啟用三個 API：**Places API**（後台地址自動完成用）、
     **Geocoding API**（地址轉經緯度用）、**Maps JavaScript API**
     （前台顯示互動地圖用）
   - 申請至少兩把 API Key，並設好限制（金鑰外流是常見資安事故來源，
     這步不能省）：
     - 前台用的 Key：限制成只能被你的網域呼叫（HTTP referrer
       restriction），因為這把 key 會出現在瀏覽器原始碼裡，任何人
       都看得到
     - 後台/伺服器用的 Key：限制成只能被你的伺服器 IP 呼叫（IP
       restriction），這把 key 才有權限呼叫 Geocoding／Places
   - 費用：Google Maps Platform 每月有一筆免費額度（依方案而定，
     一般小流量網站通常在額度內），但要記得在 Google Cloud Console
     設定**用量上限或預算告警**，避免流量異常暴衝時產生非預期費用
2. **後端**：`News`（或新的關聯表）加 `Address`／`PlaceId`／
   `Latitude`／`Longitude`／`VenueDetail` 欄位，新增/更新公告的
   API 要能收這幾個欄位、EF Core migration 加欄位——這一步要動到
   資料庫結構，會另外跟你確認要不要現在對正式資料庫跑 migration，
   不會自己動手。
3. **前台**：
   - 後台編輯器（`SPS.AdminWeb`）:地址輸入框接 Places Autocomplete
     元件，選完自動帶出 `Address`／`PlaceId`／經緯度，小編另外手動
     填 `VenueDetail`
   - `SPS.Web` 公告詳情頁：有經緯度的公告才顯示地圖（用 Maps
     JavaScript API 嵌入釘選點），沒有地點的公告（多數「產業新知」
     這類）不受影響、維持現狀
   - `/news` 列表卡片的時間/地點條列（`NewsListCard` 的 `meta`
     欄位）等地點資料真的有了再接上，現在先維持不用

拿到 API Key 之前，後端/前端的程式改動都可以先做（欄位、UI 元件、
資料流程都不需要真的呼叫得通 Google API 才能寫），但要實際測試
Autocomplete／地圖顯示這幾個互動功能，就要等你把 Key 準備好。

## 2026-09-08：搜尋功能接上真查詢（`/news`）

`SearchBar`（[SearchBar.tsx](../src/components/ui/SearchBar.tsx)）原本
是純外觀的靜態表單，關鍵字欄位/查詢按鈕點了完全沒反應——這不是這次
才漏掉，是比較早之前就存在、元件自己註解也寫明的坑。跟 Google Maps
不一樣，這個**不需要外部服務／API Key**，後端 `NewsQueryParameters`
本來就有 `Search` 參數，純粹是前端沒接，複雜度低，已直接接上：

- `SearchBar` 改成真的 `<form method="get">`，靠瀏覽器原生行為把
  欄位組成 query string、導到目前網址，不用 `"use client"`／
  `router.push`。
- 新增 `hiddenFields` prop：GET 表單送出時網址上的 query string會被
  表單欄位整組換掉，`/news` 同時有分類篩選（`?category=`）跟搜尋
  （`?q=`）兩個獨立參數，所以搜尋表單要把目前選的分類用隱藏欄位
  帶進去，不然一按搜尋分類篩選就被沖掉。
- `api.server.ts` 的 `fetchNews()` 補上 `search` 參數，並把回傳值
  從單純的 `{ items }` 改成 `{ items, backendAvailable }`：原本
  「後端連不到」跟「後端有回應但剛好 0 筆」都會觸發退回假資料，接上
  搜尋之後這個混淆會變成真的問題（搜尋一個沒有結果的關鍵字，卻看到
  一堆不相干的假資料，會誤導使用者以為那是搜尋結果）。現在
  `backendAvailable === false` 才代表連不到／噴錯，才退回假資料；
  搜尋 0 筆結果會照實顯示「找不到符合「關鍵字」的公告。」。

**已知缺口，不在這次範圍內**：`/faq`、`/serve`、`/promotion`、
`/promotion/video` 這四頁也在用同一顆 `SearchBar`，但頁面本身沒有讀

### 🐛 意外抓到的跨頁面 bug：圖片欄位是相對路徑，瀏覽器直接載入會 404

`/promotion` 是第一個真的每一筆資料都有設定封面圖的內容類型
（26 筆全部有 `coverImageUrl`，`/news` 目前 98 筆剛好 0 筆有設定
`imageUrl`，同樣的問題但沒被曝出來），一測就發現圖片全部 404。

原因：後端回傳的圖片欄位（`News.ImageUrl`、`SuccessCase.CoverImageUrl`）
是**相對於後端 API 本身**的路徑（例如
`"/api/FileManagement/{guid}/download"`），不是相對於這個 Next.js
網站——瀏覽器端 `<img>` 標籤直接拿這種相對路徑當 `src`，會拿去跟
「目前網站」的 origin 兜，變成向 Next.js 自己要一張圖，當然 404。

修正：新增 `lib/content-list-utils.ts` 的 `resolveBackendAssetUrl()`，
在資料離開 `api.server.ts`（伺服器端）前就把相對路徑轉成完整網址
（用 `NEXT_PUBLIC_API_BASE`，不是 `API_URL`——`API_URL` 在 production
可能是瀏覽器連不到的內部位址，`NEXT_PUBLIC_API_BASE` 才保證是瀏覽器
打得到的公開位址）。`fetchNews()`／`fetchNewsDetail()`／
`fetchPromotionCases()`／`fetchPromotionCaseDetail()` 都已經套用。

**這個修正跟下面這件事是兩回事，不要搞混**：轉出來的網址格式是對的
（實測用瀏覽器 devtools 確認 `<img src>` 正確變成
`http://localhost:5055/api/FileManagement/{guid}/download`），但圖片
還是載不出來，因為**本機這台後端的檔案儲存空間裡實際上沒有這個
檔案**——直接呼叫這個下載端點會回 `{"message":"文件下載失敗: File
not found: 2026/07/24/xxxxx.jpg"}`，隨機測了 3 個 guid 都是同樣的
「檔案不存在」，看起來是本機開發環境的檔案儲存沒有跟正式/其他環境
同步（資料庫裡的檔案中繼資料存在，但實體檔案沒有跟著搬過來）。這是
**環境/資料問題，不是程式問題**，換一個有實體檔案的環境（例如正式
環境，或本機檔案儲存補齊之後）圖片就會正常顯示，不用再改程式碼。

## `/serve`（服務專區）目前沒有對應的後端內容類型（2026-09-09）

（`ServeItem`）回推，需要的欄位其實跟 `News` entity 很像（Title／
Introduction／Content／Category／Picture／Tags 這幾項概念全部對得

1. **分類是兩層，不是一層**——`News`／`SuccessCase` 的分類都是單層
   （`CategoryId` 直接對到葉節點）。服務專區是「主選單分組（技術

   技術文件／知識加值／XR…）」兩層結構，`titleAside`（`ServeSubNav`）
   要靠「這個葉節點屬於哪一組、組內還有哪些兄弟節點」這組對照關係
   才能顯示同組切換。**這塊後端其實已經準備好了**：`Category` entity
   （`SPS.Domain/Entities/Category.cs`）本來就是「統一分類表」，設計
   上就支援父子階層（`ParentId`／`Children`／`HasChild`），`CategoryType`
   enum 目前有 `News`／`Product`／`Question`／`Regulations` 等值，只要
   之後加一個 `Serve`（或沿用 `General`）的分類類型，兩層分類直接用
   現成的 `Category` 表就能建，不需要另外設計資料表。
2. **詳情頁是「留資料換下載文件」，不是唯讀内容**——`/serve/[id]`
   有一份 `DownloadRequestForm`（含個資蒐集同意 modal），使用者要
   留資料才能下載附件，這比 `News`/`SuccessCase` 單純唯讀瀏覽多了
   一段「名單蒐集」的後端邏輯，需要一張表記錄「誰、什麼時候、下載
   了哪一份文件」，附件本身可以沿用現有的 `FileManagementController`
   （`News` entity 本來就有掛 `Files` collection，機制上是通的）。

這份純粹是先把「如果要做，大概要長什麼樣子」寫下來，不是這次要做的
待辦——2026-09-09 跟使用者確認過，先維持假資料、記進這份文件，等
後端真的要排這塊再一併處理。

2026-09-10 接會員登入時發現：`/member/register` 註冊 Step2 的六張

### 現況盤點

- `MemberApplication`：只有一個 `MemberRole` 欄位，`CompanyId`／
  `CompanyName`／`UnifiedSocialCreditCode` 這些企業欄位都在同一張

- `Company.Level`（`CompanyLevel`：`Basic/Standard/Premium/VIP`

  審核人，跟權益表「新興會員：文件審查＋至少 5 位專家審查」這個
  多委員評分流程對不起來（這點 9/7 稽核已經點過名，這次一併排

### 提案（5 項，供確認）

1. **`MemberRole` 加一個 `None = 0`**，代表「個人會員，還沒有

   allow null（後者要動到所有讀這個欄位、假設一定有值的地方，
   前者影響範圍小很多，傾向後者風險更低但要重新過一次所有讀取點）。

2. **`MemberApplication` 加 `ApplicantType`（`Individual`/
   `Company`）欄位**，並把 `UnifiedSocialCreditCode`／
   `ContactPerson`／`CompanyName` 這幾個「企業專屬」欄位的
   `[Required]` 改成「`ApplicantType == Company` 時才必填」的
   條件式驗證——這樣「個人會員」才真的送得出申請。

3. **`CompanyLevel` 改名對齊「卓越／新興」**，同時砍掉語意不明的

   有用到）要怎麼對應過去？照「先設計、實際還沒上線資料不多」的
   前提，還是要先看一下現有資料再定映射規則？

4. **升級流程**：`MemberApplication` 加 `ExistingMemberId`（可空，
   指向 `Member`）——有填代表這是「既有會員」送出的升級申請（可能
   是個人升級需求/供給角色，也可能是個人升級成企業），審核通過後
   **更新**這個既有 `Member`（補 `CompanyId`／改 `Role`），不是
   建一個新帳號；沒填才是全新註冊。`Member.ApplicationId` 單一 FK
   維持不動（存「最近一次」申請即可，歷史記錄如果之後要查，
   `ApplicationLog`／各張 `MemberApplication` 本身留著、用
   `ExistingMemberId` 反查就查得到，不急著另外拉一張多對多關聯表）。

   **⚠️ 2026-09-10 順著這條追蹤流程時發現的既有 bug（要跟第 4 項
   一起修）**：使用者問「企業追加角色不做輕量入口、讓既有會員走
   完整重新申請，這樣會不會漏資料核對」，追了
   `CreateMemberAndCompanyAsync`（[ApplicationReviewService.cs:460-500]
   (../../SPS.Application/Services/ApplicationReviewService.cs)）
   才發現：**這支方法對申請書上每個聯絡人都是無條件 `AddAsync`
   建一筆新的 `Member`，完全沒有先查這個 email 是不是已經有帳號**
   ——公司那邊（同一支方法上面幾行）有先用統一編號查既有
   `Company`、查到就更新／升級成 `Both`，人（`Member`）這邊沒有做
   一樣的事，兩邊處理方式不一致。且 `Member.Email` 在 DB 層完全
   沒有唯一性限制（只有普通索引），登入用的
   `GetByEmailAsync`／`AuthService.cs:65` 是 `FirstOrDefaultAsync`，
   沒有排序保證——同一個人第二次申請（企業追加角色、或之後的
   個人升級企業）如果聯絡人 email 沒變，審核通過會生出**第二筆
   `Member`**，同一 email 兩筆帳號、角色/密碼可能不同，之後登入
   會登到哪一筆變成不確定，權限也會跟著飄。

   這不是這次新設計才有的問題，是現有系統本來就有的資料完整性
   漏洞，只是這次決定「不做輕量追加入口」會提高觸發機率——修法：
   `CreateMemberAndCompanyAsync` 建 `Member` 前先用 email 查
   `GetByEmailAsync`，查到既有帳號就**更新**（合併角色/權限），
   不是無條件新建，跟第 4 項的升級流程一起修。

     重複，維持一對多即可，加總／加權平均在讀取時算，不用另外

**修正一：會員終態其實只有 4 種，不是 6 種**

PDF「(四)個人會員升級企業會員」原文：

1. 個人會員
2. 企業會員－需求端
3. 企業會員－供給端（卓越會員）
4. 企業會員－供給端（新興會員）

才會做的事，天生屬於登入後的操作，不是註冊當下的選項。

**修正二：卓越／新興的判斷條件，PDF 給了精確定義**
