# 安全性改版規劃（2026-10-21，設計討論中，尚未實作）

> **狀態：只討論設計，決定之前不動程式。** 這份文件記錄 2026-10-21 的討論結論與待決定事項，之後在這份文件上繼續討論，定案後再分期實作。
> 起因：後台「系統配置」整理時發現「啟用密碼過期」沒有實際效果，進而從 ISO 27001 角度討論登入安全該怎麼設計。

## 1. 目標

從 ISO 27001（2022 版附錄 A）的角度，把登入與存取控制設計成「依風險分級、設定與實作一致、可稽核」：

| 控制項 | 和本案的關係 |
|---|---|
| A.5.15 存取控制、A.5.16 身分管理 | RBAC 骨幹 + 少數情境判斷 |
| A.5.17 鑑別資訊 | 密碼政策、通行金鑰、復原流程 |
| A.8.2 特權存取權限 | 後台管理員強制 MFA |
| A.8.5 安全鑑別 | 驗證強度與風險相稱；新裝置重新驗證 |
| A.8.15 / A.8.16 日誌與監控 | 登入紀錄、異常通知 |

27001 本身**沒有**要求密碼定期過期、ABAC 或零信任，都是依風險評估決定；稽核看的是「文件寫的和實際做的一致」。

## 2. 現況盤點（2026-10-21 已查證）

- **後台權限是 RBAC**：`Role.Permissions` 位元欄位 + `[RequirePermission]`，細節見 [rbac-permission-design-2026-10-03.md](rbac-permission-design-2026-10-03.md)。
- **安全性設定**（`SecuritySettingsDto`，後台「安全設定」頁）：登入失敗鎖定（預設關，5 次、30 分鐘）、首次登入強制改密碼、密碼過期（預設關，90 天）。
- **「密碼過期」「首次登入改密碼」目前沒有實際效果**：後端在登入時會判斷（`AdminAuthService`、`AuthService`），並在登入回應回報 `requirePasswordChange` 與原因；但**前台會員登入與後台登入都沒有讀這個回報**，使用者照常登入。同樣影響會員管理裡「要求會員下次登入改密碼」。而且判斷只發生在登入當下，一直保持登入的使用者不會被攔下。
- **通行金鑰（Passkey/FIDO2）已有**：`Fido2Service`，會員與後台都有端點。但註冊與登入時「使用者驗證（UserVerification）」與「可探索憑證（ResidentKey）」都設成 **Preferred**（偏好），不是 Required（必要）。
- **沒有 TOTP**（驗證器 App）。
- **登入狀態**：accessToken／refreshToken 放 httpOnly cookie；會員 refresh token 有效期 7 天。
- **登入紀錄**：`ActionLogService.LogLoginAsync` 已記錄登入成功／失敗、IP、User-Agent。
- 沒有裝置概念（不知道是不是同一台裝置），也沒有位置判斷。

## 3. 已討論的共識

1. **不做密碼定期過期。** 27002:2022 的 5.17 與 NIST SP 800-63B 都不建議定期強制更換（使用者只會改成 Password1、Password2）。改為：密碼夠長、比對外洩密碼清單、登入失敗鎖定、**懷疑外洩時才強制更換**，再加 MFA。
2. **RBAC 為骨幹，不做完整 ABAC。** 只在少數敏感動作加上情境判斷（裝置是否受信任、登入風險、是否剛重新驗證），等於輕量的 ABAC／風險式驗證。
3. **零信任的落法 = 持續驗證，不是只信一次登入**：新裝置、風險升高或敏感動作時要求重新驗證，不是每次都打擾使用者。
4. **後台管理員強制 MFA**（特權帳號，稽核重點）。
5. **通行金鑰登入本身就是 MFA，不需再疊加**——前提是「使用者驗證」必須是 Required（驗證本人：生物辨識或裝置 PIN），Preferred 時只確認在場，只剩一個因素，不能算。

## 4. 設計草案

### 4.1 驗證強度（誰要什麼）

| 對象 | 登入方式 | 要求 |
|---|---|---|
| 後台管理員 | 通行金鑰（UV 必要） | 不需再 MFA |
| 後台管理員 | 密碼 | 必須再加第二因素（TOTP 或通行金鑰），**不能只靠密碼** |
| 一般會員 | 通行金鑰（UV 必要） | 不需再 MFA |
| 一般會員 | 密碼 | 平常照舊；**新裝置或風險升高才要求第二因素**（風險觸發，不強制每次） |

已註冊通行金鑰的管理員，是否關閉密碼登入（避免降級攻擊）見「待決定」。

### 4.2 通行金鑰設定調整
- 註冊與登入的 `UserVerification` 改為 Required；`ResidentKey` 視需要改為 Required。
- 每個帳號建議至少註冊兩把（兩台裝置，或一把實體安全金鑰當備援），避免單一裝置遺失被鎖在外。
- 同步型通行金鑰（iCloud／Google 帳號同步）方便但把部分安全性交給雲端帳號；裝置綁定型（實體安全金鑰，如 YubiKey）等級最高。管理員是否限制只接受裝置綁定型見「待決定」。

### 4.3 受信任裝置（新裝置重新驗證）
- **不用瀏覽器指紋**（UA、IP 不可靠）。改成：登入並通過驗證後，由伺服器發一個放在 httpOnly cookie 的「受信任裝置憑證」，綁定該帳號；伺服器端只存雜湊、有到期日、可撤銷。
- 換瀏覽器、清 cookie、憑證到期＝視為新裝置，要重新驗證。
- 需要新資料表（裝置：帳號、憑證雜湊、首次與最近使用時間、IP、User-Agent、到期、撤銷狀態），可能要 migration。

### 4.4 位置風險
- 只取**國家或城市等級**（GeoIP），當作風險訊號：位置明顯異常（例如短時間跨國）→ 要求重新驗證並通知，**不直接拒絕登入**。
- 原因：手機換基地台、公司出口 IP、VPN 都會誤判，擋太嚴會一直打擾使用者。

### 4.5 新裝置的驗證方式
- 管理員：通行金鑰或 TOTP。
- 會員：通行金鑰，或 Email 一次性驗證碼（平台已有寄信能力）。

### 4.6 帳號復原（最弱的一環）
- 復原流程不能比主要驗證弱：通行金鑰遺失後若能只靠「Email + 密碼」重設，攻擊者就繞過了 MFA。
- 候選做法：事先註冊多把通行金鑰、備用復原碼、管理員帳號由另一位管理員核可後重設。

### 4.7 通知與可見性
- 新裝置登入寄通知信。
- 會員／管理員可看到自己的登入紀錄與已登入裝置清單，可一鍵登出其他裝置（撤銷工作階段）。

### 4.8 敏感動作的情境檢查（輕量 ABAC）
候選清單：匯出資料、企業名錄取得聯繫窗口、刪除、角色與權限管理、系統設定變更。判斷依據：裝置是否受信任、最近是否重新驗證、登入風險。

### 4.9 密碼政策
- **拿掉「啟用密碼過期」選項**（或預設關閉並隱藏）。
- 新增：密碼長度下限、外洩密碼比對、登入失敗鎖定預設開啟。
- 「首次登入強制改密碼」與「要求會員下次登入改密碼」要讓它真的生效（前台與後台登入讀 `requirePasswordChange` 並導向改密碼流程）。這類是「管理員主動指定」或「疑似外洩」才強制，不是定期。

### 4.10 個資與保存
- 裝置、IP、位置都屬個人資料：隱私說明要告知用途、只蒐集必要資料、訂定保存期限（個資法最小蒐集原則）。

## 6. 預估影響範圍

- **後端**：`AuthService`／`AdminAuthService` 登入流程、`Fido2Service`、新增裝置與 TOTP 相關服務、風險判斷。
- **資料庫**：第二期起需要 migration（裝置資料表、TOTP 秘鑰、復原碼）。
- **前台**：會員登入頁、會員中心（登入紀錄、裝置清單、通行金鑰管理、改密碼流程）。
- **後台**：登入頁、安全設定頁（選項調整）、管理員 MFA 註冊流程。
- **文件／稽核**：存取控制政策、密碼與驗證政策、登入日誌保存期限。
